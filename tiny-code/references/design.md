# 設計

## 原則

外部依存を境界の外に置き、小さな契約を介して利用する。依存先を変更するときは接続部と組み立てだけを変更し、中心の処理を保つ。

差し替え可能性のために実装を増やしすぎない。必要な境界を設けたうえで、責務、型、設定、依存を最小限にする。

実装を小さくする前に要求と実際の処理経路を理解する。誤った箇所への小さな変更は最小実装として扱わない。

## 最小の解決策を選ぶ

コードを書く前に次の順で確認し、要求を満たした段階で止める。

1. そもそも作る必要があるか。確認できない将来の要求には作らない。
2. 同じ役割の実装が既にあるか。ある場合は再利用する。
3. 標準ライブラリで実現できるか。できる場合は利用する。
4. 実行環境や利用基盤の標準機能で実現できるか。できる場合は利用する。
5. 導入済みの依存で実現できるか。新しい依存を増やさず利用する。
6. 一つの式や既存処理への小さな追加で済むか。済む場合は構造を増やさない。
7. いずれでも満たせない場合だけ、動作する最小の実装を書く。

複数の案が同じ大きさなら、境界条件まで正しく扱える案を選ぶ。短さのために壊れやすい方法を選ばない。

## 不具合を直す

報告された症状だけを直さず、破られた前提を所有する箇所で直す。変更する共有処理の呼び出し元を確認し、同じ原因を持つ経路を一度に直せる場所を選ぶ。

外部形式の問題は接続部、業務上の判断は中心の処理、組み立ての問題は入口で扱う。各呼び出し元へ同じ回避処理を追加しない。

## 外部依存との境界

Plugin、SDK、外部API、保存先など、中心の処理とは独立して更新されるものに境界を設ける。外部都合で形式や失敗条件が変わらないものには、将来の可能性だけを理由に境界を追加しない。

利用側が必要とする操作、値、失敗だけを小さな契約として定める。外部固有の型、応答、例外は接続部で契約に合う形へ変換し、中心の処理へ持ち込まない。

```text
中心の処理 → 小さな契約 ← 接続部 ← 外部依存
```

契約の実装は入口で組み立てて渡す。処理の途中で外部依存を探索または生成しない。依存先を差し替えるときは、接続部と入口だけを変更する。

## 実装を小さく保つ

既存の仕組みや標準機能で要求を満たせる場合は、新しい基盤や実装を追加しない。既存の契約で足りる場合も新しい抽象を作らない。

次のものは作らない。

- 契約や変換を担わない中継層
- 将来の可能性だけに備える差し替え口
- 一つしかない処理を一般化する基底型
- 動作確認できない設定や拡張機構

削除を追加より優先し、複雑な仕組みより既知の単純な方法を選ぶ。外部依存を隔離する契約は必要な境界として扱うが、それ以外の一実装専用の抽象は作らない。

一方、外部形式の変換や小さな接続部は省かない。入力検証、データ損失を防ぐ失敗処理、セキュリティ、アクセシビリティも削減対象にしない。

設計後に、外部依存を別の実装へ替えた場合の変更箇所を確認する。中心の処理まで変わる場合は契約から外部の詳細が漏れている。変更箇所が不要に多い場合は境界や組み立てを小さくする。
