# Tiny Code

変更理由が異なる処理を疎結合にし、変更の影響を局所化することを最優先にする。その条件を満たす範囲で作らずに済ませ、必要な変更可能性を少ない構造で保つ。

## 疎結合の目的

一つの変更に対してAgentが読み、直し、確認する範囲を小さく閉じる。層や型を増やすことではなく、変更を所有する箇所と隣接する契約だけで判断を完結できる状態を目指す。

Plugin、SDK、外部APIなど独立して更新される部品は接続部の外側へ置く。破壊的変更が発生しても、接続部、組み立て箇所、契約確認の変更で吸収し、業務上の規則を変更せずに済む状態を目指す。

次の根拠がある場合に境界を設ける。

- 管理主体や公開時期が異なる
- 独立したバージョンや公開契約を持つ
- 入出力形式や失敗条件が外部都合で変わる
- 変更時に別の確認手段を必要とする

変わる可能性があるという理由だけでは境界を増やさない。

## 判断の軸

次の優先順位で構造を判断する。

1. 別々に変わる処理を分け、変更の影響を局所化する。
2. 疎結合を損なわない範囲で、新しい責務やコードを作らない。
3. 変更範囲を狭めるための変換や接続には必要なコード量を使う。

同じ理由で変わる処理はまとめ、安定した規則から変化しやすい実装を参照しない。独立して変わる見込みがない箇所へ、形式上の層や差し替え口を作らない。

## 作らないことを次に選ぶ

新しい基盤を追加する前に、既存の基盤とその標準機能だけで要求を満たせるか確認する。満たせる場合は新しい基盤を追加しない。

必要な境界と所有関係を定めた後で、既存の振る舞いと契約だけで要求を満たせるか確認する。満たせる場合は実装を追加しない。

複数の案が同じ変更可能性を持つ場合は、新しい責務、設定、依存を増やさない案を選ぶ。将来の可能性だけを理由に差し替え口や互換処理を用意しない。

ただし、作らないために独立した処理を直接結合しない。接続部や明示的な変換を省いて外部の詳細を中心へ漏らすことは、実装の削減ではなく変更可能性の低下として扱う。

## 変更理由を見つける

変更対象を読むときは、次の要素が互いに独立して変わるか確認する。

- 業務上の判断と状態の変化
- 入出力の形式と利用者への見せ方
- データの保存方法と外部サービス
- 実行環境、時刻、乱数などの外部条件
- 独立して更新されるPlugin、SDK、枠組み

変更理由が異なる場合は直接結合せず、用途に必要な値と操作だけを境界として定める。単にファイルを分けるのではなく、片方の変更がもう片方へ伝わらない形にする。

## 依存の方向

業務上の規則を内側へ置き、通信、保存、表示などの詳細を外側へ置く。外側は内側を利用してよいが、内側は特定の枠組みや外部サービスを知らない状態にする。

```text
外部の詳細 → 変換と接続 → 用途の処理 → 業務上の規則
```

必要な外部操作は利用側の言葉で小さな契約として定める。契約の実装は組み立て箇所から渡し、処理の途中で探索または生成しない。

## 境界を明示する

外部の形式や型は接続部で用途に合う値へ変換する。外部サービスの応答、保存形式、枠組み固有の型を中心の規則まで持ち込まない。

失敗も境界で意味を変換する。外部固有の例外をそのまま伝えず、用途の処理が判断できる失敗として表す。表示、再試行、記録はそれぞれの責務を持つ外側で決める。

境界を越えるデータには用途に必要な項目だけを持たせる。便利さのために外部の巨大なオブジェクトを渡し、暗黙の依存を増やさない。

PluginやSDKのマニフェスト、機能情報、バージョン条件も外部形式として接続部で解釈する。外部更新により業務上の規則まで変更が必要になった場合は、要求自体が変わったのか、外部の概念が契約から漏れているのかを確認する。

## 冗長性を区別する

すべての重複を同じ問題として扱わない。変更を妨げる冗長性は除き、変更を分離する冗長性は許容する。

除く対象は次のとおり。

- 同じ境界内に同じ知識を複数箇所へ記述した状態
- 契約や変換を担わない単なる中継
- 名前や層をそろえるためだけの型とファイル
- 確認できる要件を持たない設定や拡張機構

一方、次のコードは行数が増えても残してよい。

- 外部形式を内部の値へ移す明示的な変換
- 独立した機能同士を結合しないための小さな接続部
- 変更理由が異なる領域に置かれた似た処理
- 境界の契約と変換を保証する確認

構文が似ているだけで共通化しない。知識と変更理由を共有するときだけ共通化し、独立した変更を一つの抽象へ閉じ込めない。

## 変更を実装する

1. 要求から独立して変わる要素を特定する。
2. 判断やデータを所有する箇所と必要な境界を決める。
3. 所有箇所、隣接する契約、組み立て箇所、対応する試験を確認範囲として定める。
4. 既存の振る舞いと契約だけで要求を満たせるか確認する。
5. 変更が必要なら、境界を越える値と操作を定める。
6. 所有箇所へ変更を実装し、外側で形式を合わせる。
7. 変更の影響が意図した範囲に収まるか確認する。
8. 偶発的な冗長性だけを取り除く。

既存の境界が適切なら再利用する。境界が責務と一致しない場合は、互換用の中継を重ねず所有関係が明確になる最小範囲で直す。

一度に置き換えられない外部依存は、変更対象の周囲に接続部を置いて段階的に分離する。移行中も新しい直接依存を増やさない。

不具合は、破られた前提を所有する箇所で直す。入力形式の問題は接続部、業務判断の問題は規則、組み立ての問題は入口で扱う。

## 確認範囲を閉じる

境界が成立している場合は、所有箇所、隣接する契約と接続部、組み立て箇所、対応する試験に確認を限定する。念のためという理由だけで無関係な領域まで探索しない。

次の証拠がある場合だけ確認範囲を広げる。

- 契約が別の経路からも利用されている
- 共有状態や副作用が境界を越えている
- 公開形式や通信規約が変わる
- 試験、実行結果、呼び出し関係が境界外の影響を示す

範囲を広げた場合は、その根拠と新しい確認境界を明確にする。

## 確認する

業務上の規則は外部サービスなしで確認できる形にする。接続部では値と失敗の変換を確認し、実際の通信や保存を使う確認は外部契約が必要な範囲へ限定する。

独立して更新される外部部品については契約確認を置く。外部部品の更新に対して接続部と契約確認だけを変更し、業務上の規則を変更せず対応できるかを確かめる。

既存の試験方法へ合わせ、変更した責務と境界を確認する。試験のためだけに本体へ新しい公開口や共有状態を追加しない。

試験は次のいずれかを検出するものに絞る。

- 通常の運用では発覚しにくい問題
- 発生時の影響や重要度が高い問題
- Plugin、SDK、外部APIなどの外部依存により壊れやすい契約

修正した事実だけを根拠に、その修正内容を保証するための試験を追加しない。修正内容が前述の条件を満たす場合だけ必要な試験を追加する。定数、内部構造、文言を実装と同じ形で言い直す試験は、それ自体が公開契約でない限り作らない。

簡潔さを理由に、入力検証、認証と認可、データ保全、明示された要件を省略しない。これらも所有箇所を明確にして局所化する。

## 応答

変更結果を先に示す。設けた境界、意図して残した冗長性、確認を閉じた範囲のうち、判断に必要な内容だけを説明する。確認範囲を広げた場合は根拠も示す。

少ない行数ではなく、少ない結合で変更できるコードを書く。
